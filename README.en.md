# An accumulative "second brain" on top of Claude Code

> Language: English · Русский: [README.md](README.md) · Presentation (PDF): [presentation-en.pdf](presentation-en.pdf) · [Русская презентация](presentation-ru.pdf)


A layer that turns a one-off chat with an AI assistant into an accumulative, self-improving system. Every session adds knowledge to long-term memory. Every mistake becomes a lesson. Every rule is enforced by machine, not by human memory. Background timers tidy things up at night, and external research is pulled into memory for free.

**What this document is.** A description of the architecture and design principles of one personal system built on top of Claude Code between roughly 11 April and 17 June 2026 (about 2.2 months). It is a dated record of what was built and how, not a claim of being first. The applied projects, their domains, servers and clients are deliberately not disclosed. This is only about the layer itself.

**Terms.** A *hook* is a script Claude Code runs by itself at a set moment (before a tool, after it, at the end of a turn). A *skill* is a command of the form `/name`. *Launchd* is the macOS task scheduler (similar to cron), running without an open chat. An *embedding* is a numeric "fingerprint of meaning" of text for semantic search. A *K-note* is an atom of knowledge. A *lesson* is a record of "symptom, cause, fix". A *MOC* (Map of Content) is a navigation hub for a topic.

---

## In one paragraph

A normal AI chat starts every conversation from zero. It forgets context, repeats mistakes, and makes up facts. This system fixes exactly those three problems. Knowledge goes into long-term memory and is found three ways: by index, by meaning, by the link graph. Mistakes are recorded as lessons and stop repeating, and if they do repeat, a repeat detector fires. Facts get checked: the assistant searches memory first and backs conclusions with real command output instead of "recalling". The difference from a folder of notes is that the system rests on verifiable principles from knowledge theory and engineering practice, implemented as executable code rather than good intentions.

## Architecture: four loops

1. **Memory.** What we know (6 storage tiers).
2. **Learning.** How new knowledge is born, checked, decays and is revived (8 phases).
3. **Execution and protection.** Rules and hooks keep work on protocol and block mistakes in real time.
4. **Observation.** Timers, audits and a dashboard watch that the first three loops stay alive.

Cross-cutting principles sit on top of the loops. They are the core of the system.

---

## Design principles

### 1. Zettelkasten: atomic linked knowledge

Niklas Luhmann's idea: knowledge is stored as atoms (one note equals one thought) linked by references; structure comes from maps of content, not folders.

How it is implemented: one file equals one note, a linter catches notes that are too short and duplicate ids. 2789 wiki-links across 437 notes (6.38 links per note), zero notes without outgoing links, a separate linter catches broken links. 27 maps of content are assembled by a script from metadata. A bidirectional backlink index is rebuilt daily. Difference from Luhmann: most links and all maps are generated by scripts rather than by hand. Stronger in coverage, weaker in organic serendipity.

### 2. Knowledge graph: a directed scale-free network

Links between atoms form a graph. 1434 nodes, 12073 edges, average in-degree about 8.4, a power-law distribution with hubs. The top hub, a meta-security rule, has 413 citations and is used by almost every session. A separate code-dependency graph is built by parsing syntax, with decay protection: if a new graph is under 10% of the old one, it rolls back.

### 3. Accumulative self-evolution (the Karpathy approach)

The system evolves on its own. Executable artifacts with metrics were found:

- A nightly fitness loop: one change up to 50 lines, a metric measurement (search precision plus canary plus drift), rollback via git on regression.
- Four-tier memory: semantic, procedural (lessons), episodic (session index), working (snapshots).
- Hybrid search by keywords and by meaning at once.
- Reflection after every session (a "session voice" field in 359 files).

A sign of maturity: part of the approach was deliberately rejected as premature. What works is taken; the form is not copied.

### 4. Cross-project memory as a load-bearing structure

A lesson learned in one project automatically protects the others. Lesson search is three-tier: lessons of the project itself, lessons of related projects, a random by-meaning selection from any project. A single base of 140 lessons and 73 rules applies to all projects.

### 5. Versioned, portable storage

Memory is code. Several git repositories, one-way sync after every edit, auto-commit and auto-push on a timer. A hook blocks hardcoded absolute paths in new code so that moving to another machine or changing the username does not break the hooks.

## Working with external repositories

A separate loop: the system continuously collects, analyzes and standardizes external GitHub repositories, and integrates only what is actually needed.

- Auto-collect. A hook catches every GitHub link from four sources (session text, the user prompt, web requests, README reads) and records it in a registry.
- Analyze. Stars, license, freshness, releases, dependencies are checked per repo. A separate tool checks "am I reinventing something that already exists" before building anything new.
- Standardize. Each repo gets a uniform card and a status: use as is, adopt the idea, watch, or reject.
- Selective integration. Not the whole repo is taken but only the needed part, often rewritten for the local stack rather than copied. A license with no usage rights or a dependency on a paid SaaS means rejection.

As of 17.06.2026 the registry holds 69 repositories (114 cards) sorted by status: catalog (21), adopt pattern (24), installed and in use (11), watch (5), rejected (4). Example decisions: one tool for removing AI writing tells was installed as is; a budget tracker was taken as an idea only and rewritten for the local stack; another was rejected over a license with no usage rights.

The point: external experience is not dead weight and is not copied blindly. The essence is extracted from a repo, checked for applicability, and only what the system needs enters it, in the right form.

## Self-development

A principle running through the whole system: anything that can be automated, studied quickly and reduced to its essence without spending the human's time is done automatically. The human gets a finished conclusion, not raw material.

- External research via NotebookLM runs by itself, and the answer is distilled into a knowledge atom and placed in memory.
- External repositories are collected, parsed and reduced to a card with a verdict. The human sees the result, not raw code.
- Mistakes turn into lessons by themselves, lessons surface by themselves at the right moment, contradictions between them are caught automatically.
- Nightly timers repair, index, back up and check the system while the human is away.
- A nightly fitness loop tries small edits, measures the result, and rolls back whatever worsened a metric.

The result: the system does not wait for commands on routine work. It studies incoming material, drops the excess, keeps the essence and builds itself out. The human spends time only on what needs a human decision.

## Learning loop: eight phases

Capture, review, promotion, indexing, decay, supersession, recall, linking. Each phase is run by its own hook or timer. This is the main mechanism that separates an accumulative system from a normal chat. Known weak spot: the capture queue stalls, the review phase lags behind intake.

---

## Protection loop: rules and hooks

The core idea: a rule you "have to remember" gets forgotten. So critical rules are turned into blocking hooks that fire on their own and can stop an action. Protection is three-layered: before the action, after the action, before the answer.

What gets blocked in practice: destructive commands; the words "done, fixed, correct" without proof from real command output; launching an agent without a narrow scope; editing a file with an unread cross-model review; hardcoded absolute paths in new code; finishing a turn with unclosed checks.

73 rules with priorities and conflict resolution. Every rule with a state dependency must have an enforcing hook, otherwise it counts as an "orphan" and is caught by an audit. This is the most mature domain of the system.

## Observation and quality control

- Dashboard (21 sections, a single state file): cost, knowledge, discipline, queues, blocks. Over a month the assistant cost under $2, the main research is free.
- Cross-model control: a second model (Codex/GPT) independently reviews code changes and catches bugs the primary model missed. Review quality is calibrated by a live false-positive rate (about 20%).
- Free research via NotebookLM: deep topic research at no cost, answers are distilled and pulled into memory as knowledge atoms.
- Three-model debates: for assessments and brainstorms, three independent models generate blind, then cross-attack and synthesis. This guards against shared hallucinations of a single model.
- External inputs: notes and photos from the phone via a messenger bridge with text recognition; free keyless web search; a "am I reinventing something that exists" check before building anything new.

## How it grew

The system was not built at once but in four phases:

- Foundation (before 11 April 2026): rules as text files, still without enforcement.
- Skeleton (11 April): the main backbone of memory, hooks and commands set up in a single day.
- Saturation (April and May): growth in lessons and rules, a shift from reminders to hard blockers.
- Hardening (June): a kill switch, a circuit breaker, cross-model control, a rule-coverage audit.

More than half of all commits were made in the last month, so the pace is rising, not falling.

## Maturity

On the CMMI scale (1 ad-hoc, 5 optimizing), 10 domains, average about 2.9, between "repeatable" and "defined". Two domains (Rules, Lessons) at level 4 (Managed, measured). No level 5 yet.

Rule coverage by enforcers: of 73 rules, 22 are suitable for a hard blocker, the other 51 by nature require judgment (style, assessments) and are checked by a judge model. Of the 22, blockers cover 12. The main limiter is the gap "code works, behavior lags", treated by turning reminders into blockers.

## Honest limitations

A strong system must withstand criticism of its own metrics. These are not "growth points" but structural weaknesses that numbers do not close.

- **Over-engineering risk.** 357 hooks and 73 rules are maintained by one person on one machine. Some hooks have not fired in a long time, possibly dead code. The system can count firings but not the benefit of each firing.
- **Meta-work competes with the product.** A large part of two months went into the tool itself rather than the projects it was built for. The balance "investment in the tool versus working with the tool" is measured nowhere.
- **Metrics are self-referential.** Maturity, discipline, false-positive rate: the system rates itself by its own criteria. There is no external anchor, no A/B comparison "with the system versus without it". One of the metric calculators once "lied" (showed the maximum on failure), a direct proof of the risk.
- **Bus factor of one.** Everything depends on one person, one Mac, one working style. Backups reduce the risk of data loss but not the risk of losing the context carrier: the "why it is so" lives in the author's head plus in 2242 files that few could unfold without him.
- **A machine Zettelkasten loses serendipity.** Links are generated from metadata. That gives coverage and zero orphans but loses the very thing Luhmann invented the method for: the unexpected hand-made link that sparks an idea. A machine links the similar, a human links the unexpected.
- **Even a self-documenting system drifts.** While preparing these reports a gap was found between documentation and code (the docs lagged). A system whose goal is not to lose context loses its own sync. If this drifts, so does whatever has not been noticed yet.

## Bottom line

In about 2.2 months an accumulative, self-improving layer on top of Claude Code was built: about 2242 memory files, about 74,800 lines of code, 357 protective hooks, 76 nightly timers, 73 rules serving a portfolio of 14 projects. It rests on verifiable principles: Zettelkasten (atoms plus 12073 links plus auto-maps), a knowledge graph (scale-free, hubs), accumulative self-evolution (a fitness loop, episodic memory, with a deliberate refusal of cargo-cult), cross-project transfer of knowledge, and versioned portable storage. It studies incoming material on its own, drops the excess, keeps the essence and builds itself out. Maturity about 2.9 of 5, the main front is closing the gap "code works, behavior lags" with enforcement instead of reminders. The pace is not slowing.
